# Симуляція втрати вузла

Модуль розрахунку наслідків вилучення одного підприємства та знімок графа, який використовує карта StayHard. Папка також містить вихідний CSV і дані для відтворення метрик важливості. Підключення до бази даних і ключі доступу не потрібні.

| Файл | Що містить |
| --- | --- |
| `simulation.js` | Незмінений модуль зі сторінки симуляції. Функція `analyse(nodes, edges, removedId)` порівнює мережу до та після вилучення одного вузла і всіх його зв’язків. Працює в Node.js та браузері. |
| `graph.json` | Мінімальний знімок від 11.10.2026: 44 067 підприємств та 22 407 зв’язків усіх шарів. Для підприємства збережені `id` і `name`, для зв’язку — `from`, `to`, `kind`. `metadata` містить дату, походження, кількість записів і початкові налаштування шарів. |
| `contracts.csv` | Усі 65 897 вихідних записів ClearSpending у початковому порядку; збережені 10 колонок, які читає розрахунок. Це проєкція початкового CSV: предмети закупівлі та інші невикористані колонки сюди не перенесені. |
| `metrics.json` | Вихідні та нормовані метрики для 18 216 учасників розрахунку: V_eff, посередництво, SSR, HHI, стан R, CCI та межі доступної оцінки. Ідентифікатор `id` дозволяє зіставити результат із `graph.json`. |
| `metrics-run.json` | Дата зрізу, часовий коефіцієнт, параметри вибірки посередництва, коефіцієнти CCI, контрольні суми файлів і очікуваний відбиток зваженого графа. |
| `court_audit_input.jsonl` | 500 вихідних карток судових справ, які початковий скрипт читає для аудиту достатності доказів. Вони не дали перевірених значень R та не створюють числового внеску в індекс. |
| `README.md` | Опис даних, алгоритму, результатів та приклад запуску. |

## Які дані використовуються

- `nodes[].id` — унікальний ідентифікатор вузла, переважно ІПН, збережений як рядок. `name` допомагає знайти підприємство, але не впливає на розрахунок.
- `edges[].from` та `edges[].to` — ідентифікатори двох підприємств, між якими зафіксований зв’язок.
- `edges[].kind` — тип зв’язку. Його використовують для вибору шарів перед викликом симуляції.

| Тип | Походження | Кількість | Увімкнений початково |
| --- | --- | ---: | --- |
| `contract` | Постачальник → замовник за картками закупівель ClearSpending — «Госзатраты» | 21 303 | Так |
| `parent` | Дочірня → материнська компанія за корпоративними профілями та деревом групи | 818 | Так |
| `supplier` | Відносини постачання, наведені в профілях | 38 | Так |
| `bank` | Банківські відносини з профілів | 84 | Ні |
| `related` | Пов’язані компанії з профілів | 153 | Ні |
| `successor` | Правонаступництво з профілів | 11 | Ні |

Контрактний шар побудований із **34 231 договору** за 2022–2026 роки, де встановлені обидві сторони. Повторні договори між тією самою парою постачальника й замовника об’єднані в один напрямлений зв’язок. У початковому архіві було 65 897 записів, але записи без установленого постачальника не створювали контрактних зв’язків.

Джерело контрактів — [ClearSpending](https://clearspending.ru/); корпоративних відносин — знімок профілів і дерева групи з [«Війна і санкції» ГУР](https://war-sanctions.gur.gov.ua/), перенесений із БД проєкту. Це знімок відомих відносин на зазначену дату. Вузли без координат та без зв’язків збережені, щоб відтворити загальні лічильники сайту.

Початково увімкнені `contract`, `supplier`, `parent`: разом **22 159 зв’язків**. Типи `bank`, `related`, `successor` належать до спільного перемикача `other`; увімкнення його додає 248 зв’язків. Функція `analyse` сама не читає налаштування шарів: передати потрібно вже відібраний масив зв’язків.

## Що рахує симуляція

Модуль будує список сусідів кожного підприємства. Він знаходить усі зв’язані групи, потім пропускає обраний вузол і повторює пошук груп. Напрямок і вага зв’язку в цьому порівнянні не використовуються. Зв’язки різних типів між тією самою парою залишаються окремими записами в лічильнику зв’язків; для пошуку сусідів повтори об’єднуються.

Суми й дати договорів, оцінки важливості CCI, посередництво та частки постачальників не потрібні цьому алгоритму й не включені в `graph.json`. Вони збережені окремо для розрахунку важливості. Вилучення вузла не змінює вихідні масиви.

Основні поля результату:

| Поле | Значення |
| --- | --- |
| `before`, `after` | Кількість підприємств (`nodes`), записів зв’язків (`edges`), груп (`components`), підприємств у найбільшій групі (`largest`) та груп з одного підприємства (`isolated`). |
| `removedEdges` | Скільки зв’язків обраного підприємства вимкнено. |
| `fragments` | На які частини розділилася початкова група обраного вузла; найбільша частина перша. |
| `detached` | Кількість підприємств у всіх менших частинах цієї групи. Вони залишаються в мережі. |
| `newlyIsolated` | Ідентифікатори підприємств, які після вилучення втратили всіх сусідів. |
| `neighbours` | Прямі партнери вилученого вузла до вилучення. |
| `fragmentById` | `Map`: ідентифікатор підприємства → номер частини. Допомагає інтерфейсу виділяти утворені групи. |
| `connectedPairs`, `pairLoss` | Усередині `before` / `after` кількість неупорядкованих пар підприємств у спільній групі, а `pairLoss` — її зменшення. Воно включає також пари з вилученим вузлом. |

Розділення груп означає, що між ними більше немає ланцюжка **збережених у цьому графі відносин**. Це не є розрахунком зупинки виробництва або фізичних маршрутів поставок. Попередньо розрахований CCI під час цієї симуляції не перераховується.

## Запуск

Із цієї папки, за наявності Node.js, виконайте приклад:

```sh
node - <<'JS'
const {analyse} = require('./simulation.js');
const graph = require('./graph.json');
const layers = {...graph.metadata.defaultLayers};
const edges = graph.edges.filter(edge => {
  const layer = ['contract', 'supplier', 'parent'].includes(edge.kind)
    ? edge.kind : 'other';
  return layers[layer];
});

// Приклад: навчальний заклад — МГТУ «СТАНКИН».
// Замініть рядок на id потрібного підприємства з graph.nodes.
const removedId = '7707003506';
const result = analyse(graph.nodes, edges, removedId);
console.log(JSON.stringify({
  enterprise: graph.nodes.find(node => node.id === removedId).name,
  before: result.before,
  after: result.after,
  removedEdges: result.removedEdges,
  fragmentSizes: result.fragments.map(group => group.length),
  detached: result.detached
}, null, 2));
JS
```

До вилучення в початкових шарах: **44 067 підприємств, 22 159 зв’язків, 27 001 група, 14 122 підприємства в найбільшій групі**. Результат після вилучення залежить від обраного вузла й увімкнених шарів.

Для підключення у браузері завантажують `simulation.js` звичайним `<script>`; функція доступна як `window.NetworkSimulation.analyse`. `graph.json` читають через `fetch` із локального або вебсервера.

Ця папка містить розрахункову частину. Карта, червоні лінії, масштабування та перебіг анімації належать до інтерфейсу сайту (`app.js`, HTML, стилі та бібліотека карти) і сюди не включені.

## Як відтворити метрики важливості

Додані файли розрахунку в інших папках репозиторію:

| Файл | Для чого потрібний |
| --- | --- |
| `../src/cci_pipeline.py` | Початковий код розрахунку: перевірка ІПН, об’єднання договорів у напрямлені пари, ваги й довжини, V_eff, посередництво, SSR/HHI, нормування та формула CCI. Математичний код збережено без змін. |
| `../docs/CCI_METHODOLOGY_UK.md` | Повний опис формул, правил обробки відсутніх значень та обмежень моделі. |
| `../requirements/requirements-cci.txt` | Три бібліотеки з фіксованими версіями. NetworkX 3.2.1 відповідає версії початкового розрахунку; це суттєво для відтворення вибіркового посередництва. |
| `../schemas/cci_assessment.schema.json` | Перевірка структури одного запису результату. |
| `../schemas/leaderboard_cci_1.1.schema.json` | Перевірка всього масиву результатів. |

Вже наявні в репозиторії залежності: `src/supplier_enrichment.py` містить перевірку контрольних цифр ІПН; `config/russian_defence_entities.json` додає чотири довідкові профілі до 18 212 учасників договорів; `reports/graph_aggregate_audit_20261010/validation.json` записується до аудиторського переліку контрольних сум і не змінює ваги або коефіцієнти метрик.

`contracts.csv` зберігає номер і закон договору, дату, ІПН та назву замовника, ІПН та назви постачальників, суму в RUB, початкову валюту й URL джерела. JSON-масиви постачальників усередині CSV збережені без перетворення. Усі записи, зокрема без постачальника, залишені для відтворення перевірок: 34 231 двосторонній договір створює зв’язки; 31 666 записів без постачальника не створюють їх.

Повний початковий CSV займає близько 455 МБ. Вилучення шести колонок, які скрипт не читає, зменшує розмір без зміни використаних значень. Контрольні суми повного CSV та опублікованої проєкції наведені у `metrics-run.json`; ці файли не є побайтово однаковими.

Із **кореня репозиторію** виконайте:

```sh
python3 -m venv outputs/cci-reproduction/.venv
outputs/cci-reproduction/.venv/bin/python -m pip install -r requirements/requirements-cci.txt
outputs/cci-reproduction/.venv/bin/python src/cci_pipeline.py \
  --contracts node-loss-simulation/contracts.csv \
  --profiles config/russian_defence_entities.json \
  --courts node-loss-simulation/court_audit_input.jsonl \
  --snapshot-date 2026-10-11 \
  --decay 0.5436890126920764 \
  --betweenness-k 512 \
  --seed 20261011 \
  --output outputs/cci-reproduction/leaderboard.json \
  --report-dir outputs/cci-reproduction
```

Розрахунок має відтворити **18 216 вузлів, 21 303 спостережувані напрямлені пари та 21 301 пару з додатною вагою**. Числові метрики можна порівняти з `metrics.json`. Абсолютні шляхи до доказів і файлів у повторно створеному результаті залежать від місця, де розташований ваш репозиторій.

У `metrics.json` оцінки збережені на шкалі 0–1, на сайті вони множаться на 100. `cci` залишається `null`, бо підтверджених входів для R немає. `cci_lower` — сума відомих внесків, `cci_upper` — вона ж плюс коефіцієнти невідомих складових. Це межі пропусків даних, а не оцінка похибки вибіркового посередництва.
