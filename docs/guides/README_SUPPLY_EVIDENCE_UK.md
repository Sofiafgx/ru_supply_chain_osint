# Витягування доказів залежностей із документів

Узгоджені правила від 10.10.2026. Машинна структура результату:
[schemas/supply_evidence.schema.json](../../schemas/supply_evidence.schema.json).
Загальна методологія: [config/research_methodology.json](../../config/research_methodology.json).

## Джерело та доказовість

Аналізувати текст конкретного документа, а не інструкцію щодо його аналізу.
Зберігати фактичний URL або null, тип документа й походження: локальний файл,
ідентифікатор документа, дату отримання та контрольну суму, коли вони відомі.
Не вигадувати URL, реквізити, дати, відсотки, обсяги чи інтервали.

- DIRECT: джерело прямо формулює відповідний факт.
- INDIRECT: у джерелі є конкретна ознака, але висновок потребує умовиводу.
- UNKNOWN: достатнього доказу немає.

`text_proof` містить точну цитату з аналізованого тексту. За відсутності цитати
весь блок має UNKNOWN, скалярні значення null, список артикулів порожній.
Якщо цитата підтримує лише частину полів, решта залишаються null навіть у DIRECT.
Невідоме булеве значення — null; false потребує доказу заперечення.
Порожній список артикулів означає відсутність витягнутих артикулів.

DIRECT характеризує прямоту твердження у джерелі, а не незалежну перевірку
його істинності. Відрізняти доводи сторони від установлених судом обставин;
у цитаті зберігати слова «позивач стверджує», «суд установив» тощо.
Для INDIRECT записувати лише те, що підтримує ознака, без категоричного висновку.
Поточна схема має одну оцінку доказовості на блок: якщо поля спираються на різні
рівні доказів, обирати INDIRECT і зберігати цитати для кожного заповненого поля.

## П'ять блоків

1. **supplied_item.** Назва компонента й артикули. Специфікація або технічне
   завдання — прямий доказ; загальний опис закупівлі чи каталог — непряма ознака.
2. **target_product.** Виріб і підсистема. Прямий доказ має пов'язувати саме
   витягнутий компонент із виробом. Окрема згадка зброї в документі недостатня.
   Збіг артикулів із зовнішньою документацією потребує окремого походження
   цієї документації; за його відсутності зв'язок лишається UNKNOWN.
3. **supplier_replaceability.** Окремо фіксувати ознаки єдиного джерела та
   необхідність повторної сертифікації. Закупівля в єдиного постачальника
   або повторні закупівлі не доводять, що альтернатив немає. Вимога сумісності
   сама по собі не доводить необхідності повторної сертифікації.
4. **disruption_impact.** Розрізняти прострочення, заявлені збитки, затримку
   випуску та підтверджену зупинку. Позов через прострочення може прямо
   підтверджувати предмет позову; `production_stoppage_confirmed` лишається
   null без окремого доказу зупинки. Часовий збіг — INDIRECT, не доказ причини.
5. **recovery_time_ttr.** Зберігати тільки документовані дати тієї самої події,
   процесу та виробничого обсягу. `ttr_days` обчислюється як різниця
   `t_full_recovery - t_event` у календарних днях лише за підтвердженого
   відновлення повної базової потужності. Цитата має підтверджувати вхідні дати
   та повноту відновлення. Частковий запуск не дорівнює повному відновленню.
   `t_last_unrepaired` і `t_first_repaired` зберігають межі спостереження;
   вони не замінюють `t_full_recovery`, якщо повнота не встановлена.
   Нормативні строки закупівлі, випробувань або запуску аналога можуть бути
   INDIRECT із цитатою, але фактичний `ttr_days` залишається null.

## Напрям постачання та математичні моделі

Для руху товару використовувати напрям **постачальник → замовник**.
Ролі позивача й відповідача не визначають цей напрям. Потрібне пряме
формулювання обов'язків сторін у договорі або виклад цих обов'язків у рішенні.
Субпідряд потребує окремого підтвердження; наявність двох зв'язків постачання
сама по собі не доводить субпідряд. Схема п'яти блоків не містить полів сторін
чи ребра: такі дані зберігати в окремому записі зв'язку з власною цитатою.

Сума контракту не призначається автоматично як v(S) чи w(F). Вона може бути
входом моделі, якщо явно визначено економічний зміст, одиниці та спосіб обліку.
Перед обчисленням Myerson Value визначити гравців, мережу комунікацій,
характеристичну функцію, період і правила щодо невідомих даних. Для ESV
додатково визначити повну назву й конкретний варіант методики.
Зв'язність може бути окремою модельною метою; вона не підтверджує здатності
виробляти виріб. Без специфікації числові оцінки моделей залишаються null.

## Валідація

JSON Schema перевіряє типи, обов'язкові блоки, допустимі рівні доказовості,
цитату для DIRECT/INDIRECT і порожні значення для UNKNOWN. Перевірку форматів
дат та URL потрібно ввімкнути у валідаторі.
Семантична перевірка окремо підтверджує наявність цитати в тексті, її достатність
для кожного поля, атрибуцію твердження, порядок дат і правильність обчислення TTR.
Структурно валідний JSON сам по собі не є підтвердженням фактів.
