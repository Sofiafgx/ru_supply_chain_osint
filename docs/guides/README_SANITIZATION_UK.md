# Фільтр придатності до фактичних розрахунків

Фільтр `src/data_sanitization.py` працює за принципом zero imputation: нічого не заповнює, не підставляє середні значення і не змінює початкові архіви. Він створює окрему очищену копію та журнал відхилень.

Запуск:

```sh
.venv/bin/python src/data_sanitization.py --root . --output outputs/sanitization_20261010
```

Результати:

- `sanitization_report.json`: об'єкт із `sanitization_summary` та `cleaned_dataset` у запитаному форматі; лічильники — числа.
- `audit_details.json`: точні шляхи, SHA-256, кількість записів у кожному файлі, причини відхилення, помилки і межі аудиту.
- `rejected_records.jsonl`: місце кожного відхиленого запису, `is_eligible_for_calculation: false`, причини та кількість скинутих полів. Вміст початкового запису залишається в архіві.

Автоматично скануються нормалізовані JSONL/NDJSON, JSON-масиви записів та JSON-конверти `records`. Сирі відповіді, кеші, службові завдання, бази даних, стиснені архіви, CSV і книги не включені в цей звіт. Повторні копії входів рахуються як окремі перевірені записи; однакові підтверджені записи до виходу потрапляють один раз. Вкладені BOM перевіряються як частина батьківського запису, а не як окремі записи лічильника. Лічильник скидань включає поля відхилених записів; початкові `null` не рахуються як скидання. Помилка читання означає `audit_complete: false` і ненульовий код завершення.

Шляхи зі `synthetic`, `smoke`, `examples`, `tests`, `fixtures`, `mocks` та демонстраційні/макетні назви виключаються. Перевіряються також вкладені прапорці синтетики й метадані походження. `verified: true` не скасовує виключення синтетичного джерела. `verified` має бути JSON-логічним значенням, а не рядком чи числом.

Підтвердження запису потребує явного `verified: true`, URL джерела, ідентифікатора конкретного документа або цитати та часу збирання з часовим поясом. Відсутність цих атрибутів виключає запис із розрахунків. Вилучення не означає, що запис сфальсифіковано: він може бути фактичним кандидатом, який ще не пройшов документальну перевірку. Фільтр не здійснює нової зовнішньої перевірки достовірності документа.

Потужність, TTR/TTS/REI, запаси, попит і норми витрат зберігаються лише за наявності доказу саме відповідного поля. Наприклад:

```json
{
  "field_evidence": {
    "tts_days": {
      "verified": true,
      "source_url": "https://source.example/document/1",
      "document_id": "1",
      "quote": "Цитата з перевіреного документа",
      "value": 30
    }
  }
}
```

Це схема, а не фактичні дані. Значення `value` повинне точно збігатися зі значенням поля. Для потужності додатково потрібні `method: "bottom_up_bom"` та непорожній масив `inputs` із підтвердженими документами й значеннями. Фільтр перевіряє наявність доказового пакета, але не виконує і не підтверджує арифметику bottom-up самостійно. Непідтверджені кількості у BOM з `requires_manual_verification: true` стають `null`; підтвердження зберігається у документованому об'єкті `manual_verification` з `verified: true`.

Числа не вилучаються за самою величиною: документальна сума договору 550 або 550000000 не є припущенням про потужність. Порожнє поле не стає нулем. Сценарії та кандидати спостережень не стають фактичними входами.

`SupplyChainProxyModel.build_network` застосовує той самий фільтр перед додаванням ребер. Параметр потужності моделі без `capacity_evidence` стає `None`. `Ledger.observe` відкидає синтетику і зберігає очищені непідтверджені спостереження лише з ознакою непридатності. Представлення `graph_edges` і звіт метрик додатково виключають старі записи без позитивної ознаки придатності. Історичні таблиці лишаються архівом, а не готовим набором для обчислень. Хардкодований `KNOWN_BOM` вилучено; старий BOM API повертає порожній список до появи документального збирача.

Низькорівневі математичні функції в `analytics/resilience.py` є загальними формулами. Вони не встановлюють походження переданих чисел або кортежів: дані потрібно подавати через фільтр, граф моделі або захищене представлення реєстру. Edge-Based Shapley не реалізований у цьому проекті; очищення не створює нового розрахунку цього показника.
