# Асинхронний збір договірних зв’язків

`src/contract_links_async.py` — окремий CLI для Python 3.9+. Залежності: `httpx`,
`BeautifulSoup4`, `Pydantic 2`; додатково `pypdf` для тексту опублікованих PDF КАД.
Початкові шість ІПН вже внесено у скрипт. Існуючі збирачі проєкту не змінено.

## Запуск

Для наявного локального корпусу без FTP, API чи проксі:

```sh
python3 src/contract_links_async.py \
  --local-contracts data/collection_20261008/exports/contracts.csv \
  --output outputs/local_contracts_new \
  --kad --kad-html saved_case.html
```

Локальний режим відбирає **цільового замовника АБО цільового постачальника**,
на відміну від мережевого режиму взаємних цільових пар нижче. Протилежна сторона
має пройти перевірку контрольних цифр ІПН; анонімні постачальники не створюють ребра.
`matched_contract_candidates.csv` зберігає всі збіги з причиною відбору/відхилення,
а `contracts.ndjson` містить лише підтверджені пари та поля `customer_inn`,
`customer_name`, `supplier_inn`, `supplier_name`, `contract_id`, `sign_date`,
`price_rub`, `product_description`. Пропущені реквізити — `null`.
Імена кількох постачальників із паралельних CSV-масивів не зіставляються навмання.

`--kad` у локальному режимі не робить мережевих запитів. `--kad-html` приймає
збережені HTML карток; для підтвердження потрібні канонічна адреса картки КАД,
обидва точні ІПН і протилежні процесуальні ролі. HTML пошуку сам по собі не
доводить контракт чи спір між сторонами. Нерозпізнані картки та порожні
пошуки описуються у `reports/status/coverage.json`; 15 пар зберігаються в `kad_pair_queue.json`.
Неповне локальне покриття пошуків не трактується як відсутність справ.

```sh
python3 -m pip install -r requirements/requirements-contract-links.txt
python3 src/contract_links_async.py --proxies config/private/proxies.txt --output outputs/contracts_run_01 --kad
```

Один повний URL проксі на рядок: `http://host:port`, `https://host:port` або
`socks5://host:port`; дозволено `user:password@host:port`. Рядки з `#` пропускаються.
Проксі надає оператор; вбудованого пошуку безкоштовних проксі немає. Порожній
список спричиняє помилку. HTTPS до джерела працює і через HTTP CONNECT.
Проксі ротуються на кожен запит, повтор і перенаправлення. Перевірка сертифікатів
джерела вимкнена (`verify=False`), для HTTPS-проксі теж задано відповідний TLS-контекст.
Прямого мережевого fallback і читання проксі зі змінних середовища немає.

Використовуйте новий порожній каталог кожного запуску. `--max-pages 100` обмежує
кількість сторінок кожного пошуку; у Checko цей ліміт включає картки договорів.
`--concurrency 4` обмежує одночасні HTTP-запити; `--interval 2` задає мінімальний
інтервал між початками запитів до одного хоста для всіх проксі разом.
Мережеві збої, 429 та 5xx повторюються обмежено, з паузами. 401/403 і видима
антибот-перевірка позначають пошук як невдалий. CAPTCHA не розв’язується.

## Семантика і вихідні файли

«Взаємні» означає: **обидві сторони належать до переліку цільових ІПН**,
замовник відрізняється від постачальника. Договір A → B не вимагає договору B → A.
Роль кожного цільового ІПН перевіряється за реквізитами самого договору.
Сторони з невідомим ІПН не дозволяють довести зв’язок, тому не потрапляють до результату.

- `contracts.ndjson`: рівно вісім запитаних полів. Дати ISO `YYYY-MM-DD`, ціни —
  точні JSON-числа з `Decimal`, відсутні значення — `null`. Невідомий текст,
  дата або ціна не замінюються штучними значеннями. Невалідний формат — помилка.
- `court_cases.ndjson`: справи з підтвердженими протилежними процесуальними ролями, якщо увімкнено `--kad`.
- `execution.ndjson`: дослівні опубліковані статуси виконання, відомості про приймання
  й оплату. Якщо їх немає, дані не вигадуються; укладення договору не доводить виконання.
- `reports/status/coverage.json`: статус кожного джерела, ІПН і ролі. Вичерпання ліміту,
  повторення сторінки або нерозпізнана структура означають неповне покриття.
- `provenance.ndjson`: джерело й пошукова роль кожного запису, пов’язані SHA-256
  канонічного рядка. Точні дублікати усуваються; різні версії одного договору
  зберігаються для перевірки, без мовчазного злиття суперечливих реквізитів.
- `raw/`: відповіді джерел за SHA-256 вмісту для повторного розбору.

Код завершення `0`: усі запитані пошуки завершені; `2`: помилка або часткове
покриття; `130`: переривання оператором. Успішні пошуки зберігаються навіть за
помилок інших джерел. Дані пошуку, що завершився помилкою, відкидаються; тому
`contracts.ndjson` може бути порожнім при невдалому доступі — це не доказ
відсутності договорів. NDJSON пишеться через тимчасовий файл і атомарну заміну.

## Адаптери джерел і межі перевірки

Clearspending використовує публічний запит вебінтерфейсу
`https://clearspending.ru/api/gw/filtered-contracts/` із `customer_inn` / `supplier_inns`, `page`, `page_size`.
Його формат перевірено на збереженій у цьому проєкті відповіді 08.10.2026.
Фільтри ролей звірено з поточним JS вебінтерфейсу 10.10.2026; роль додатково
перевіряється локально за реквізитами договору. Масиви імен та ІПН кількох постачальників не поєднуються навмання:
без явних об’єктів постачальника відповідне ім’я залишається `null`.

ЄІС (`zakupki.gov.ru`): адаптер `collect_zakupki()` опрацьовує реєстри контрактів
44-ФЗ і договорів 223-ФЗ. Пошук за ІПН виконується в кожному реєстрі, потім
завантажуються знайдені первинні картки. Ролі підтверджуються тільки реквізитами
замовника та окремих постачальників у картках. Поля ІПН та імен зі сторонніх
розділів не використовуються. Посилання на сторінки виконання відкриваються,
коли вони опубліковані в картці. Дослівні підписи статусу, приймання та оплати
зберігаються в окремому файлі; підсумкове «виконано» із них не обчислюється.
Номер реєстру можна взяти з явного реквізиту або параметра первинної картки.
Нерозпізнана структура реквізитів чи пагінації спричиняє помилку покриття.
**Живу сумісність HTML-адаптера ЄІС ще не підтверджено**: зовнішня перевірка
сторінки реєстру 10.10.2026 завершилася тайм-аутом. Тести використовують
синтетичні приклади карток; вони не підтверджують поточну розмітку ЄІС.

Checko: пошук `/search?query=ИНН` може повертати список або перенаправляти на
точний профіль. ІПН звіряється із заголовком профілю. Скрипт знаходить фактичні
посилання `role=customer` та `role=supplier` у розділі `#contracts`; посилання
загального каталогу не вважаються профілем. HTML розбирається лише за явними
підписами реквізитів. У живому запуску 10.10.2026 профілі двох коректних цільових
ІПН відкрилися, але їхні розділи контрактів повернули 429 після обмежених повторів.
Чотири інші ІПН дали явну відповідь «профіль не знайдено». HTML, завантажений
лише JavaScript, потребує іншого адаптера. Поточне завантаження контрактів Checko
не підтверджено через обмеження доступу.

Для точного вибору розділів можна передати `--checko-sections sections.json`.
Структура JSON: об’єкт із ключами ІПН; значення містить `customer` та `supplier`,
кожне — непорожній масив фактичних HTTPS-адрес розділів на `checko.ru`.
Використовуйте адреси, скопійовані з доступних карток; не підставляйте шаблони
адрес. Цей параметр замінює пошук розділів, але не адаптує їхню HTML-структуру.

КАД: `check_arbitration_pairs(client, pairs, pages=100, pdfs=False)` — окрема
асинхронна функція. Перетинає результати пошуку кожного ІПН і перевіряє обидва
точні ІПН у структурованому розділі учасників картки. Далі обов’язково підтверджує
протилежні ролі позивача та відповідача; без них запис не додається. Вихідні поля:
`party_a_inn`, `party_b_inn`, `plaintiff_inn`, `respondent_inn`, `case_number`,
`registration_date`, `claim_amount_rub`, `dispute_text`, `source_url`, `evidence_urls`,
`dispute_evidence`. Ролі замовника/постачальника зі справи не виводяться.
За `--kad` перевіряються всі 15 цільових пар, навіть якщо договорів не виявлено.
Спільна справа не доводить, що вона стосується саме знайденого договору. Пошук не обмежено періодом. Поточні підтримувані селектори учасників:
`#case-participants`, `.case-participants`, `[data-role="participants"]`.
Ролі учасників шукаються всередині цього розділу за
`[data-role="plaintiff"]` / `[data-role="respondent"]`, класами або ID з такими
назвами. Якщо розділ недоступний або формат інший, перевірка пари завершується помилкою.
**Селектори картки не підтверджено живим запуском: пошук КАД 10.10.2026 повернув HTTP 451.**

Сума вимог витягується тільки біля «Цена иска» або «Сумма требований» з явно
зазначеною валютою рублів. Різні знайдені суми дають `null`; інші грошові згадки
не стають сумою позову. Опис спору — дослівні фрагменти з недопоставкою, простроченням, порушенням
умов поставки або відхиленнями за якістю сировини/матеріалів, позначені `keyword_candidate`, без автоматичного висновку про вину.
Немає тексту — `dispute_text: null`, а не висновок, що порушення не було.
`--kad-pdfs` додає читання тексту фактично опублікованих PDF на доменах КАД/РАС.
Скани без текстового шару потребують OCR, якого в цьому скрипті немає.
Для додаткових пар: `--pairs pairs.json`, масив `[party_a_inn, party_b_inn]`. Напрям процесуального позову встановлюється
за карткою, а не порядком ІПН у масиві.

Внутрішні вебзапити й HTML джерел не мають гарантованої стабільності. Транспорт,
валідація й запис реалізовані для робочої експлуатації; повну production-сумісність
усіх адаптерів можна підтвердити лише після запуску через доступні оператору
проксі й перевірки поточних карток. Документація джерел:
[Checko](https://checko.ru/integration/api/contracts),
[Clearspending](https://clearspending.ru/docs), [КАД](https://kad.arbitr.ru/).

## Перевірки

```sh
python3 -m unittest discover -s tests -p test_contract_links_async.py -v
```

22 тести перевіряють ротацію, налаштування TLS, відхилення сторонніх редиректів,
антибот-відповіді, пагінацію, фільтрацію ролей і цільових пар, `null`, точність
грошей та неоднозначність імен/сум. Один тест розбирає збережену справжню
відповідь Clearspending, якщо вона присутня у проєкті. Тести із синтетичними
відповідями не підтверджують доступність сайтів.
