# Парсер патентів підприємств

Запускати з кореня проєкту. Парсер шукає публікації чотирьох підприємств за кириличними й латинськими варіантами назв; остаточно перевіряє власника за бібліографічними полями, а не згадками в тексті. Класи МПК: **H01Q, G01S, G06F**. Публікації різних стадій одного патенту зберігаються окремо за номером із кодом виду документа.

```sh
PYTHONPATH=src .venv/bin/python -m pip install -r requirements/requirements-patents.txt
.venv/bin/python src/patent_cli.py plan
.venv/bin/python src/patent_cli.py collect --source google --limit 50 --pages 1 --output outputs/patents/google.jsonl
```

`plan` створює `outputs/patents/search_plan.json` з посиланнями на пошук і прикладами `assignee:"..."`. За замовчуванням пошук обмежений RU. Власників перевіряємо за назвами з оригінальних метаданих; канонічні назви є групуванням варіантів, а не підтвердженням історичної тотожності юридичних осіб. Коротка назва «НИИ КП» може потребувати ручної перевірки.

Для одного підприємства:

```sh
.venv/bin/python src/patent_cli.py collect --assignee 'АО "НИЦЭВТ"' --pages 2 --limit 20 --output outputs/patents/nicevt.jsonl
```

Google Patents не надає в цьому рішенні гарантованого API: пошук використовує вебендпоінт `/xhr/query`, який може змінитися. Спочатку отримуємо кандидатів із відповідними префіксами CPC, потім виконуємо ширший пошук за власниками, щоб знайти документи без CPC. Остаточний фільтр завжди за МПК. Якщо спрацював ліміт, ширший пошук може не початися. Резервний шлях — CSV, завантажений через інтерфейс Google Patents, або прямі URL документів:

```sh
.venv/bin/python src/patent_cli.py collect --csv exported_patents.csv --output outputs/patents/from_csv.jsonl
.venv/bin/python src/patent_cli.py collect --url https://patents.google.com/patent/RU2396592C2/ru --output outputs/patents/one.jsonl
```

На вебсторінці Google часто присутня лише CPC. Парсер **не підміняє МПК кодами CPC**: якщо МПК немає в метаданих, читає поле `(51)` першої сторінки офіційного PDF. За відсутності текстового шару або однозначного поля документ відхиляється з причиною `missing_or_non_target_ipc`. OCR у цій версії не реалізовано. PDF використовується для перевірки МПК; формула й описи схем беруться з текстових розділів HTML/XML.

## ФІПС та локальні документи

```sh
.venv/bin/python src/patent_cli.py collect --source fips --depth 2 --limit 30 --output outputs/patents/fips.jsonl
.venv/bin/python src/patent_cli.py collect --source fips --url 'https://fips.ru/URL_КОНКРЕТНОГО_БЮЛЕТЕНЯ' --output outputs/patents/bulletin.jsonl
.venv/bin/python src/patent_cli.py import saved_patents/ --output outputs/patents/imported.jsonl
```

Підтримуються HTML Google Patents, HTML ФІПС з полями INID `(11)/(13)/(51)/(54)/(73)/(43 або 45)` і окремими заголовками «Описание изобретения» та «Формула изобретения/полезной модели», XML ST.36 (включно з просторами імен і пакетами `patent-document`), нормалізовані JSON/JSONL. Імпорт папки рекурсивний. Для нестандартної верстки ФІПС слід підготувати нормалізований JSON; не вважайте кожну версію вебреєстру підтриманою. Самостійні PDF та скани потребують попередньої підготовки тексту й метаданих.

Під час перевірки **10.10.2026** головна сторінка бюлетенів ФІПС повернула HTTP 403. Колектор записує це в аудит і завершується з кодом 1; обходу обмежень доступу немає. Навігаційні сторінки можуть мати `parse_error`, але їхні посилання все одно обходяться в межах `--depth`. Це обмежений обхід HTML-посилань, а не повний доступ до пошукового реєстру чи JavaScript-навігації. Найкраще подавати прямі посилання на документи/конкретні бюлетені.

## Як визначається множник

Один рядок JSONL відповідає одному технічному фрагменту та одному цільовому власнику. Пошук охоплює формулу й опис: АЦП, ПЛИС, тракт прийому, генератор тактових імпульсів, многоканальный, количество каналов. Додатково розпізнається полосовий фільтр у контексті цих термінів.

- `detected_architecture_channels`: `values` — явні числові варіанти, `symbol` — нормалізоване `N`, `evidence` — текстові підстави.
- `calculated_component_multiplier`: об’єкт за компонентами або `null`. Для «4 канала; каждый приемный канал содержит АЦП» маємо `ADC: {per_channel: 1, r_kj: "N", value: 4, component_type: "functional_component"}`.
- Для двох АЦП у кожному з восьми каналів: `per_channel: 2`, `r_kj: "2*N"`, `value: 16`.
- Для символічного `N` без числа зберігається формула, але `value: null`.
- Альтернативи `4, 8, 12`, діапазони, прототипи, заперечення, спільні компоненти й змішані приймальні/передавальні канали мають `null` та `review_reasons`.
- Число каналів саме по собі не визначає кількість АЦП/ПЛІС. Не запозичуємо числа з інших пунктів формули. Для опису допускається короткий сусідній абзац із числом каналів; цей зв’язок залишається евристикою.

Додаткові поля: `source_url`, `canonical_assignee_name`, `ipc_codes`, `section`, `paragraph_index`, `matched_terms`, `review_reasons`, `drawing_urls`, `interpretation`. Посилання на зображення зберігаються; графічна топологія схем не розпізнається. `raw_snippet_quote` — текст джерела після декодування HTML і нормалізації пробілів, без перекладу чи переказу.

Множники описують **функціональні компоненти патентної архітектури**. Вони не є підтвердженою нормою закупівлі фізичних мікросхем: багатоканальний АЦП може реалізовувати кілька функціональних перетворювачів в одному корпусі, а фільтр може бути дискретним. Поле `interpretation` явно фіксує цю межу.

## Аудит і відтворюваність

Поряд із JSONL записується `.audit.json`: оброблені номери, відхилення, помилки, кількість фрагментів, обрізання пошуку. У `data/patent_cache/` залишаються байти HTTP-відповідей та URL/SHA-256/кодування в окремому JSON. Повторні запуски використовують кеш; для оновлення задайте нову папку `--cache`. Мінімальна пауза — `--delay 1`; повтори лише для тимчасових HTTP-помилок. Кеш містить також пошукові відповіді; не імпортуйте його рекурсивно як нормалізовані патенти.

Пошук за варіантами назв, `--pages`, `--limit`, часовий зріз джерела та неповна індексація можуть обмежувати покриття. Порожній JSONL не означає відсутності патентів: перевірте аудит. Для більш рівномірного пілота запускати кожне підприємство окремо. Наявні старі публікації з кодом `A` можуть не мати всіх потрібних бібліографічних полів; вони відхиляються явно.

## Перевірка без мережі

```sh
PYTHONPATH=src .venv/bin/python -m unittest tests.test_patent_parser -v
.venv/bin/python src/patent_cli.py import examples/patent_documents.synthetic.jsonl --output outputs/patents/synthetic_demo.jsonl
```

Усі номери й тексти в `examples/patent_documents.synthetic.jsonl` **вигадані для тестування**, а не результати дослідження підприємств. Тести перевіряють множники, альтернативи, спільні/заперечені компоненти, прототипи, розмежування пунктів формули, фільтри власника/МПК, HTML/XML та JSONL-аудит.

Пілот 10.10.2026: `outputs/patents/pilot_vniir.jsonl` містить один реальний технічний фрагмент (RU2760977C1), без підтвердженого множника. Пілоти інших трьох підприємств із лімітом 3 публікації дали порожній JSONL; причини по кожній публікації — у відповідному аудиті. Для ВНИИР-Прогресс ліміт був 6. Це перевірка працездатності, а не повна патентна вибірка. Демонстрація числового множника знаходиться тільки у `synthetic_demo.jsonl`. Формат рядків описано також у `schemas/patent_records.schema.json`.
