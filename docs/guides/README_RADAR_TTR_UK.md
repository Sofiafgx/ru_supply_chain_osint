# Радарний часовий ряд Sentinel-1 GRD

`src/sentinel1_radar_ttr.py` використовує `asf_search` для пошуку та завантаження
Sentinel-1 IW GRD високої роздільності з VV+VH через NASA ASF.
Вбудовані обидва задані полігони; координати — [довгота, широта], WGS84.
Вони задані прямокутниками: статистика описує весь прямокутник, включно із
землею та іншими об'єктами всередині, якщо це не точний контур даху.

## Встановлення та запуск

Потрібні Python 3.9+, залежності й окремо ESA SNAP із Sentinel-1 Toolbox
(актуальні версії можуть називати його Microwave Toolbox) та виконуваним `gpt`.
Для завантаження потрібен NASA Earthdata Login із доступом до ASF.
SNAP автоматично отримує точні орбіти й DEM через мережу; потрібні достатня
пам'ять і місце для повних ZIP GRD. Один архів може займати кілька ГБ.

```bash
python3 -m pip install -r requirements/requirements-radar-ttr.txt
export EARTHDATA_TOKEN='ваш_токен'
python3 src/sentinel1_radar_ttr.py \
  --t-event '2025-01-31T12:00:00+02:00' \
  --gpt '/Applications/snap/bin/gpt' \
  --out data/radar_ttr/example/result.json
```

Дата в прикладі умовна: підставте встановлену дату інциденту.
Альтернатива токену — `EARTHDATA_USERNAME` та `EARTHDATA_PASSWORD` у середовищі.
Дата без часу означає 00:00 UTC; час без часового поясу не приймається.
Авторизація не зберігається у вихідному JSON.

Пошук без авторизації та без SNAP:

```bash
python3 src/sentinel1_radar_ttr.py --t-event '2025-01-31' \
  --catalog-only --out data/radar_ttr/catalog.json
```

Інші контури: `--aoi buildings.geojson`; формат GeoJSON FeatureCollection,
кожна ознака містить `properties.object_id` і Polygon/MultiPolygon.

## Обробка та порівняння

Вікно пошуку включне: [t_event − 30 днів, t_event + 180 днів].
ASF запитується окремо для ASCENDING і DESCENDING, з повною пагінацією.
Використовується режим IW, VV+VH, GRD_HD; продукти інших режимів і поляризацій
не змішуються. Відбираються сцени, які повністю покривають полігон.
Хмарність не використовується. Реальний інтервал між спостереженнями може
перевищувати 6–12 днів через план знімання, пропуски та доступність супутників.
Якщо вікно виходить у майбутнє, будуть лише вже доступні сцени; повторіть запуск пізніше.

SNAP: Read → Apply-Orbit-File → Remove-GRD-Border-Noise → ThermalNoiseRemoval
→ Calibration (лінійне σ⁰ VV/VH) → Subset із буфером приблизно 2 км
→ Range-Doppler Terrain-Correction (SRTM 1Sec, UTM, сітка 10 м)
→ окремі одноканальні GeoTIFF VV та VH.
Калібрування виконується до обрізки. Помилка отримання точної орбіти зупиняє
обробку відповідної сцени. Немає terrain flattening чи нормалізації до γ⁰:
вони змінили б вимірювану величину. Сітка 10 м не означає роздільність 10 м.
Спекл пригнічується просторовим усередненням у полігоні, без додаткового
фільтра, який міг би змішувати дах із сусідніми об'єктами.

Середнє: `mean_backscatter_db = 10 * log10(mean(sigma0_linear))`.
Пікселі відбираються за центрами, без ваги часткового перетину на межі;
NoData, нулі, від'ємні та нечислові значення виключаються.
Мінімум: 20 придатних пікселів і 95% придатності від усіх центрів у полігоні.
Повне покриття полігону растром перевіряється окремо.

Порівняння окреме за супутником, відносною орбітою, напрямком і поляризацією.
`orbit_number` — абсолютна орбіта; групування за нею було б помилкою,
оскільки вона змінюється на кожному прольоті. Одна дата в одному ряді є
одним спостереженням: перекривні сцени чи повторні продукти не підтверджують
зміну двічі. В JSON залишаються всі сцени; для оцінки обирається одна з
найбільшим покриттям на дату, за рівності — за scene_id. Супутники розділені,
тому окремий ряд може мати крок 12 днів навіть за наявності частіших знімків.

## Правило зміни

Це налаштовуваний евристичний детектор стійких змін, без формального p-value.

- Базовий рівень: медіана мінімум 3 доподієвих спостережень у тому самому ряді.
- Масштаб шуму: `max(0.5 дБ, 1.4826 * MAD)`.
- Падіння: щонайменше `max(3 дБ, 3 * масштаб шуму)` нижче базового рівня;
  перше спостереження — впродовж 24 днів після події.
- Падіння підтверджується двома послідовними датами із проміжком ≤18 днів.
- Відновлення: стрибок ≥2 дБ від попередньої низької точки та повернення до
  базового рівня ±1.5 дБ на двох послідовних датах із проміжком ≤18 днів.
- Помилкова/непридатна сцена та великі часові прогалини переривають підтвердження.

Параметри: `--drop-db`, `--robust-z`, `--min-baseline`, `--persistence`,
`--immediate-days`, `--max-gap-days`, `--recovery-tolerance-db`, `--recovery-step-db`.
За 30 днів бази може не вистачити трьох знімків: тоді оцінка
`insufficient_baseline`, а TTR — `null`; скрипт не вигадує базу.

`relative_change_factor = 10 ** ((mean_backscatter_db − baseline_db) / 10)`:
відношення лінійної потужності до базової; 0.5 означає приблизно −3 дБ,
1 — базовий рівень. За недостатньої бази значення `null`.

## Вихід і обмеження висновку

JSON містить `objects → object_id → time_series` із `date`, `orbit_number`,
`polarization`, `mean_backscatter_db`, `relative_change_factor`, `scene_id`,
а також напрямок, відносну орбіту, супутник, кількість пікселів і покриття.
У `assessment` окремі оцінки кожного ряду, включно з `t_drop`, `t_recovery`,
`confirmation_scene_id`, `recovery_interval` і `TTR_radar` у місяцях:

`TTR_radar = (t_recovery − t_event).total_seconds() / 86400 / 30.4`.

`t_recovery` — перша дата спостереженого повернення, підтверджена наступними
датами. Інтервал повернення сигналу — (попереднє низьке спостереження,
перше спостереження повернення]. Це не точна дата завершення ремонту.
Немає єдиного TTR, який автоматично змішує суперечливі орбіти чи VV/VH.

Статус `radar_recovery_candidate` означає стійке відновлення радарного сигналу.
Руйнування може також збільшувати розсіювання, а новий дах може змінювати його
в будь-який бік. Вологість, сніг, техніка, тіні, layover та геометрія огляду
можуть імітувати зміни. Для висновків саме про покрівлю потрібні незалежні
зображення та перевірка контурів. Відновлення сигналу не доводить відновлення
виробництва. Великі порівняльні ділянки й контрольні полігони допоможуть
перевірити вплив сезонності; автоматичної такої перевірки тут немає.

Проміжний JSON зберігається після кожної сцени; ZIP, растри, графи та `snap.log`
кешуються. Повторний запуск переобчислює оцінку й використовує завершений кеш.
JSON перезаписується за шляхом `--out`. Код виходу 2 означає помилку хоча б
однієї сцени/пошуку; подробиці — `errors` (без потенційно секретних URL),
логи SNAP — у `--cache`. Якщо треба інша версія SNAP/DEM/налаштувань,
використайте новий каталог кешу.

## Перевірка й джерела

```bash
python3 -m unittest discover -s tests -p test_radar_ttr.py
```

Тести: синтетичні падіння/відновлення, повторні дати, прогалини, розділення
орбіт, нестача бази, усереднення лінійної потужності та повнота покриття.
Обробка реального GRD потребує встановленого SNAP і Earthdata доступу.

- ASF Python API: https://docs.asf.alaska.edu/asf_search/searching/
- ASF авторизація: https://docs.asf.alaska.edu/asf_search/downloading/
- SNAP calibration: https://step.esa.int/main/wp-content/help/versions/9.0.0/snap-toolboxes/org.esa.s1tbx.s1tbx.op.calibration.ui/operators/CalibrationOp.html
- Copernicus STAC: https://documentation.dataspace.copernicus.eu/APIs/STAC.html

Copernicus Data Space — альтернативний каталог оригінальних GRD. У цьому
скрипті реалізовано один повний маршрут через ASF; клієнт Copernicus та
його авторизація не потрібні. Готові RTC часто містять γ⁰, який не можна
без пояснення називати σ⁰. Тому для цієї задачі не використано довільні
RTC-колекції Planetary Computer чи пряме читання некаліброваних DN через odc-stac.

## Хмарний запуск без SNAP

Налаштування доступу та запуск — у `docs/guides/README_RADAR_CLOUD_UK.md`.
