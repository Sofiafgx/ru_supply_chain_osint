# Збір у заданому обсязі та контроль охоплення

`src/collection_cli.py` проходить доступні сторінки результатів за планом.
Повноту та помилки потрібно перевіряти в `reports/status/coverage.json`. Поточний план `config/collection_plan.json`: 10 запитів про
верстати, електронні компоненти й композити, контракти від 01.01.2022 до
08.10.2026; весь доступний каталог C4ADS і його PDF.

```sh
.venv/bin/python src/collection_cli.py
```

Цей збір уже запускався агентом. Повторний запуск продовжує чергу у
`data/collection_20261008/collection.sqlite`, пропускаючи завершені завдання.
Сирі відповіді зберігаються у `raw/`, нормалізовані записи — у SQLite та
`exports/*.jsonl`. Таблиці для перегляду: `exports/contracts.csv`,
`exports/companies.csv`, `exports/research.csv`. `reports/audits/REPORT.md` пояснює результат,
`reports/status/coverage.json` містить докладний контроль охоплення.

У цьому проєкті середовище вже підготовлене. На іншому комп'ютері
створіть середовище Python 3.9+ і встановіть залежності:

```sh
python3 -m venv .venv
PYTHONPATH=src .venv/bin/python -m pip install -r requirements.txt
```

`contracts.csv` містить усі пошукові збіги. `matched_contracts.csv` — контракти,
у назві або в одній товарній позиції яких знайдено всі слова/словоформи запиту.
`query_matches.csv` показує запит і поля, що підтвердили текстову відповідність;
решта позначені `unverified_search_hit`. Сервіс шукає широко, тому частина
видачі не відповідає вузькому предмету дослідження. Правила словоформ явні
в `QUERY_TERMS` у коді. Це початковий відбір, не перевірка виконання контракту.
Для перегляду починайте з `data/processed/procurement/matched_contracts_summary.csv` або
`contracts_summary.csv`: вони не містять великих масивів товарних позицій;
назви довші за 2000 символів позначені як скорочені. Повні значення залишаються
у `contracts.csv` та JSONL. `data/imports/companies.csv` містить також кількість контрактів
із текстовою відповідністю (`text_match_contract_count`).

Госзатраты повертає максимум 500 результатів на запит, максимум 50 на сторінку.
Якщо результат досягає 500, колектор ділить інтервал дат навпіл і повторює
пошук для кожної половини. Це стандартні фільтри відкритого вебпошуку.
До верхньої дати запиту додається один день, а записи локально обмежуються
включним періодом: у сервісу точна верхня дата без часу виключає записи
цього дня. Якщо навіть один день досягає ліміту, завдання позначається
`capped`, повнота не заявляється. Порожня сторінка посеред пагінації — помилка,
а не успішне завершення. Збіги різних запитів не створюють дублікати контракту.

Назви компаній не ототожнюються без ІПН. Два окремі масиви назв і ІПН
постачальників не зіставляються за індексом: якщо їх декілька, назви збережені
у контрактному записі, але не призначені конкретним ІПН без доказу.
Каталог C4ADS доповнюється повними доступними HTML статей і датами публікації;
Пагінація використовується з офіційного `/category/reports/`: посилання
`/reports/page/2/` на іншій сторінці повертає 404. Документи C4ADS не
обмежуються періодом контрактів; зберігаються також старіші публікації.
супутні статті на сторінці не видаються за основний звіт. PDF зберігаються
з витягнутим текстом і номерами сторінок. Це текстовий корпус, автоматичний
аналіз фактів і таблиць PDF не виконується.
В архіві можуть бути також PDF, на які посилаються статті C4ADS, з перевірених
доменів авторів/партнерів. Для неробочого посилання зберігається помилка;
знайдена офіційна заміна позначається окремо в `reports/status/coverage.json`.

За замовчуванням один запуск обробляє до 1000 завдань із паузами між запитами.
Для Госзатрат до трьох незалежних запитів можуть бути в роботі одночасно,
але починаються не частіше разу на секунду. C4ADS обробляється послідовно
з паузою щонайменше 10 секунд згідно з `robots.txt`.
Кількість можна змінити через `--max-requests`. Якщо є `pending`, запускайте
ту саму команду для продовження. Після помилки вже зібрані записи зберігаються.
Для явного повтору невдалих завдань: `--retry-failed`. Щоб лише оновити
таблиці та звіт без мережі: `--export-only`.
Великі CSV оновлюються через кожні 250 завдань та після завершення;
`--export-every` змінює цю частоту. SQLite зберігається після кожної сторінки.

HTTP-відмова, CAPTCHA або відсутність ключа/вивантажень не замінюються
порожніми даними. Стан джерела і причина залишаються у звіті. Отримані
контракти не є доказом фактичного виконання поставки. Торговельну історію
і запас неможливо відновити лише з них.

Для іншого періоду/запитів створіть інший JSON-план і нову директорію:

```sh
.venv/bin/python src/collection_cli.py --plan my_plan.json --directory data/my_collection
```

Для справ КАД та профілів Checko у плані потрібен `company_inns` — список
ІПН. Checko також потребує власного `CHECKO_API_KEY` у `.env`.
`trade_urls` — список об'єктів `{"source":"panjiva","url":"https://panjiva.com/..."}`
із конкретними доступними профілями. Повні CSV/JSON-вивантаження зі своїх
облікових записів можна обробляти через `src/sources_cli.py`; випадкові публічні
приклади поставок не включаються у робочу вибірку.

Перевірка коду:

```sh
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -q
```

Після завершення збору перевірка архіву без мережі:

```sh
.venv/bin/python src/collection_audit.py --directory data/collection_20261008
```

`audit.json` перевіряє охоплення інтервалів дат, заявлені та отримані
кількості, дублікати між сторінками, цілісність SQLite і SHA-256 сирих відповідей.
Після аудиту `--export-only` додає його до звіту, якщо склад записів не змінився.
