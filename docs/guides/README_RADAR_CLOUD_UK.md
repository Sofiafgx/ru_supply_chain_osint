# Sentinel-1 без локального ESA SNAP: Google Earth Engine

Додано `src/sentinel1_radar_gee.py`. Обчислення радарної статистики виконує
Google Earth Engine; локально потрібні лише невеликий Python-клієнт і Shapely.
Docker, Java, ESA SNAP та завантаження повних GRD ZIP не потрібні.

## Стан розгортання

Python-клієнт установлено в `.venv`, скрипт та тести підготовлено.
На цьому комп'ютері не знайдено Docker/Podman і збереженої авторизації
Earth Engine. Реальна серверна обробка ще не виконана: потрібні project ID,
авторизація власника облікового запису та фактична дата події.
Окремі хмарні ресурси, сховища чи платні проєкти скрипт не створює.

## Первинне налаштування

1. Виберіть власний Google Cloud project із зареєстрованим доступом
   до Earth Engine та ввімкненим Earth Engine API:
   https://developers.google.com/earth-engine/guides/access
2. Установіть клієнт:

```bash
PYTHONPATH=src .venv/bin/python -m pip install -r requirements/requirements-radar-gee.txt
```

3. Авторизуйтеся зі свого облікового запису:

```bash
.venv/bin/earthengine authenticate
```

4. Запустіть із project ID і реальною датою події. Дата нижче умовна:

```bash
.venv/bin/python src/sentinel1_radar_gee.py \
  --project YOUR_PROJECT_ID \
  --t-event '2025-01-31T12:00:00+02:00' \
  --out data/radar_ttr/gee_result.json
```

Замість `--project` можна встановити `EE_PROJECT`. Альтернатива окремій
команді авторизації — `--authenticate` під час першого запуску.
Скрипт не просить передавати токен у чат і не записує його у результат.
Документація авторизації: https://developers.google.com/earth-engine/guides/auth

## Що виконується на сервері

Колекція `COPERNICUS/S1_GRD` уже містить σ⁰ у дБ після застосування файлу
орбіти, видалення граничного та теплового шуму, радіометричного калібрування
і геометричної корекції за DEM. Це не radiometric terrain flattening до γ⁰.
Провайдер визначає версію та налаштування обробки; вони можуть відрізнятися
від локального графа SNAP. Для старих сцен до липня 2015 року теплова
корекція має обмеження, зазначені Google.

Кожну сцену сервер переводить у лінійну потужність:
`power = 10 ** (sigma0_db / 10)`, а потім обчислює середнє і кількість
придатних пікселів у заданому полігоні. Локально повернуте середнє
переводиться в дБ: `10 * log10(mean_power)`.
**Не можна усереднювати готові дБ або повторно калібрувати цю колекцію.**

Використовується UTM-сітка 10 м (для обох заданих контурів EPSG:32639).
Явно задано `bestEffort=False`: сервер не може непомітно укрупнити сітку.
Середнє без ваги перетину граничного пікселя; центри пікселів визначають
включення у полігон. Загальна кількість пікселів обчислюється за незамаскованою
одиничною сіткою. Придатність — мінімум 20 пікселів і 95% покриття, окремо
для VV та VH; також перевіряється повне покриття контуром сцени.

Пошук: [t_event − 30 днів, t_event + 180 днів], IW, 10 м, VV+VH, обидва
напрямки орбіти. Використовуються обидва вбудовані полігони або `--aoi`.
Дата без часу означає 00:00 UTC. Оскільки `filterDate` в Earth Engine
виключає кінцевий час, до кінця вікна додається 1 мс.

Результат повертається пакетами по 20 сцен (`--batch-size`, максимум 100).
Дані зображень не завантажуються; один пакет — один запит статистики.
Якщо сервер повертає timeout чи помилку агрегації, спробуйте менший пакет.
Проміжний JSON зберігається після кожного пакета. Повторний запуск збирає
статистику заново та перезаписує `--out`.

## Формат результату та TTR

Збережено структуру попереднього скрипту: `objects → object_id → time_series`
і `assessment`. Додатково є `asset_id`, `quality_status`, `quality_reasons`,
кількість усіх і придатних пікселів та CRS статистики.

Детектор повторно використано з `src/sentinel1_radar_ttr.py`; цей файл повинен
залишатися поруч із новим скриптом. Для хмарного запуску залежності ASF та
Rasterio не потрібні. Відносні орбіти, напрямки, супутники та VV/VH аналізуються
окремо. Потрібні мінімум три доподієві дати; падіння й повернення підтверджуються
двома послідовними датами. Пороги та формула TTR описані в README_RADAR_TTR_UK.md.
Параметри детектора доступні також у новому скрипті через `--help`.

Непридатні дати зберігаються зі значенням `null` і переривають підтвердження.
Якщо запит пакета повністю провалився, оцінка об'єкта не виконується:
невідомі пропущені сцени могли б змінити висновок. `incomplete_collection`
та код виходу 2 означають потребу повторного збору. Порожній каталог
позначається `no_scenes`; майбутні чи відсутні знімки не підміняються даними.

Не об'єднуйте часові ряди ASF/SNAP та Earth Engine без перевірки систематичної
різниці: можуть відрізнятися DEM, орбіти, реєстрація, маски й ресемплінг.
Повернення σ⁰ — кандидат зміни радарного сигналу, не доказ нового металевого
перекриття або відновлення виробництва. Інші обмеження попередньої інструкції
залишаються чинними.

## Перевірка

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -p 'test_radar*.py'
```

Тести перевіряють перетворення лінійної потужності, маски, неповне покриття,
відсутні метадані орбіти, межу часу запиту та сумісність із детектором TTR.
Без авторизованого проєкту вони не є перевіркою виконання на серверах Google.
