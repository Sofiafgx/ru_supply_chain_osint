# Оцінка видимого відновлення покрівлі

`src/satellite_ttr.py` використовує `pystac-client`, `requests`, `shapely`.
Реалізовано збір доказів та розрахунок після ручної перевірки зображень.
Автоматичного розпізнавання нових матеріалів або сертифікації конструкцій немає.

## Вхідні дані

Центри FIRMS вбудовані у форматі **[широта, довгота]**:

- `object_1`: [57.0543, 53.9876]
- `object_2`: [55.8242, 52.0514]

Це точки. Для пошуку Sentinel-2 потрібен файл `buildings.geojson` з реальними
контурами будівель, а не довільними буферами навколо точок. Формат:
GeoJSON `FeatureCollection`, кожний `Feature` має `properties.object_id`
(`object_1` або `object_2`) і валідну геометрію `Polygon`/`MultiPolygon`.
Координати GeoJSON: **[довгота, широта]**, WGS84; кільця замкнуті.
Можна передати один або обидва об'єкти. Для одного розрахунку слід обрати
конкретну будівлю або чітко визначену групу будівель, завершення ремонту якої
оцінюється як єдине ціле. Вимога `roof_complete` стосується всього контуру.

`t_event`: ISO 8601 з часовим поясом, наприклад `2026-09-01T12:30:00+03:00`.
Дата без часу означає 00:00 UTC, тому точність 48-годинного вікна обмежується
точністю заданого часу. Календарні дні в результаті обчислюються за UTC.

## Запуск

```bash
python3 -m pip install -r requirements/requirements-satellite-ttr.txt
export FIRMS_MAP_KEY='ваш_ключ'
python3 src/satellite_ttr.py collect \
  --t-event '2026-09-01T12:30:00+03:00' \
  --end '2026-10-01T23:59:59Z' \
  --aoi buildings.geojson \
  --step-days 7 \
  --out data/geospatial_recovery/example_run
```

Дати прикладу не є встановленими датами подій. Без реального GeoJSON, дати
події та ключа FIRMS фактичний збір не виконується.
Безкоштовний ключ: https://firms.modaps.eosdis.nasa.gov/api/map_key/.
Не зберігайте ключ у репозиторії.

FIRMS Area API спочатку отримує прямокутну область; скрипт додатково
відбирає точки за сферичною відстанню ≤3 км і UTC-часом у
`[t_event, t_event + 48 годин)`. Для неміднічного початку запитуються три
календарні дати. Записи різних сенсорів зберігаються окремо і не рахуються
як незалежні події. `observed_at` — час знімання, **не точний час аварії**;
координати позначають тепловий піксель, не точний осередок пошкодження.
Аномалія може бути штатним промисловим джерелом тепла. Відсутність виявлення
не доводить відсутності події.

Для старих дат перевірте доступність продуктів FIRMS; за потреби оберіть
`--sources VIIRS_SNPP_SP VIIRS_NOAA20_SP MODIS_SP`.
Помилка джерела записується як `error`, успішна порожня відповідь — як `ok`
із `count: 0`. Якщо всі джерела помилкові, теплову частину не можна вважати
перевіреною. Перевірка архівної доступності:
https://firms.modaps.eosdis.nasa.gov/api/data_availability/.

Copernicus STAC: `https://stac.dataspace.copernicus.eu/v1`, колекція
`sentinel-2-l2a`. Застосовано `eo:cloud_cover < 15`, пагінацію та додаткову
перевірку `footprint.covers(building_polygon)` через Shapely.
Покриття контуром сцени не доводить відсутності NoData чи хмар над будівлею.

## Вихідні файли і перевірка

- `manifest.json`: геометрії, всі сцени, `scene_id`, час знімання, посилання
  на STAC та assets, теплові записи й статус кожного джерела.
- `sampling_bins`: найменш хмарна сцена в кожному вікні 5–10 днів; порожні
  вікна мають `scene_id: null`. Реальні проміжки можуть перевищувати 10 днів.
  Повний ряд сцен збережений для оцінки, щоб не втратити ранній доказ ремонту.
- `reviews.template.json`: шаблон ручної оцінки; скопіюйте в `reviews.json`.

Шаблон не перезаписується під час оцінки. Повторний збір потребує нового
каталогу результатів. Перегляньте повні знімки/вирізки, а не лише метадані.
Посилання на assets — каталог доказів; скрипт не завантажує растри.
Для захищених assets може знадобитися авторизація CDSE; FIRMS MAP_KEY її
не замінює. Quicklook цілої сцени може бути непридатним для оцінки покрівлі.

В `reviews.json` для кожного об'єкта заповніть:

1. `baseline_reference`: посилання/шлях на датоване доподієве зображення;
   `reviewer`: автора перевірки.
2. `damage_scene_id`: сцена з підтвердженим пошкодженням після події,
   `damage_verified: true`. Її `roof_complete` має бути `false`.
3. Для кожної оціненої сцени: `local_clear`, `resolution_sufficient`,
   `same_contour_verified` — логічні значення. Перевіряйте хмари, тіні,
   сніг, NoData, суміщення знімків і роздільність саме над контуром будівлі.
4. `new_roof_material`: видима поява нового перекриття; `roof_complete`:
   завершене видиме покриття всього заданого контуру без відкритих ділянок.
   Частковий ремонт має `roof_complete: false`.
5. `evidence`: точне посилання/шлях на порівняння і пояснення висновку.
   Невідомі ознаки залишайте `null`.

Sentinel-2 має канали 10/20/60 м. Для малих дахів або внутрішніх конструкцій
оцінка може бути неможлива; тоді `resolution_sufficient: false`, а TTR
залишається невизначеним. Сам спектральний колір не визначає тип матеріалу.

```bash
python3 src/satellite_ttr.py assess \
  --manifest data/geospatial_recovery/example_run/manifest.json \
  --reviews data/geospatial_recovery/example_run/reviews.json \
  --out data/geospatial_recovery/example_run/ttr_result.json
```

## Значення дат і TTR

`t_material` — перше придатне оцінене спостереження нових матеріалів.
`t_recovery` — перше спостереження завершеної покрівлі, підтверджене другою
придатною сценою щонайменше через 5 діб. Повторні продукти тієї самої UTC-дати
не є незалежним підтвердженням. Проміжна оцінка незавершеного ремонту скидає
кандидата; неоцінена потенційно придатна дата також перериває підтвердження.
Явно непридатні дати можна пропускати. Це правило якості цього скрипту,
а не офіційний норматив провайдерів. Перша підтверджена послідовність
повертається одразу; повторне пошкодження оформлюйте як окрему подію.

`ttr_days = date_UTC(t_recovery) - date_UTC(t_event)` — календарні дні
до першого підтвердженого спостереження. Це верхня спостережна межа, якщо
ремонт пов'язаний саме із заданою подією. Фактичний час завершення лежить у
`(last_incomplete, t_recovery]`; `interval.after` — виключна часова межа,
`interval.on_or_before` — включна. `ttr_calendar_days_min/max` — межі різниці
**календарних дат**, без твердження про виключність нижньої календарної дати.
Зберігаються і сцена першого завершення, і сцена повторного підтвердження.
За браку доказів `ttr_days: null`, `status: unconfirmed`; це не нуль днів.
Видимий ремонт покрівлі не підтверджує стан обладнання, несучу здатність
конструкцій або відновлення виробництва.
