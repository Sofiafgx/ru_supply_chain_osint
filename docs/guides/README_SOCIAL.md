# Історичний збір X і Threads

`src/social_cli.py` інвентаризує наявні дані, створює часові завдання та відновлює
збір з офіційних API. Цілі записані в `config/social_accounts.json`: 19 профілів X,
5 Threads і окремий невизначений Sputnik. Звіт поточного запуску:
`data/social_history/REPORT.md`.

## Доступ і запуск

Додайте у локальний `.env` власні `X_BEARER_TOKEN` та `THREADS_ACCESS_TOKEN`.
Не надсилайте токени в чат і не додавайте їх до репозиторію. X потребує доступу
до full-archive search; Threads — `threads_basic` і advanced access для
`threads_profile_discovery` сторонніх публічних профілів. Колектор не купує
кредити й не налаштовує платну підписку; запити використовують доступ вашого API.

```sh
# Лише індекс і план; без мережевих запитів.
.venv/bin/python src/social_cli.py

# Збір; до 100 сторінок за запуск, плюс запити визначення профілів.
.venv/bin/python src/social_cli.py --run --max-pages 100

# Продовження зі збережених курсорів.
.venv/bin/python src/social_cli.py --run --max-pages 100

# Явний повтор невдалих завдань після усунення причини.
.venv/bin/python src/social_cli.py --run --retry-failed
```

Код завершення `2` означає незавершений збір, зокрема відсутність ключів,
невизначені профілі або обмеження джерела. Це не успішний порожній архів.
Період фіксується на момент першого запуску мінус 60 секунд і зберігається
в `plan.json`. Для нового кінця періоду задайте `--end` із часовим поясом.
`--months 1`, `2` або `3` визначає розмір вікна; типово — 3 місяці.

## Інвентаризація та дедуплікація

Перед створенням завдань прочитуються SQLite-бази проєкту і `data/imports/posts.csv` /
`posts.jsonl`. Поточні Telegram ID не потрапляють до індексу X/Threads.
Невідомі таблиці чи помилки інвентаризації блокують мережевий збір і
записуються до `inventory.json`. Інші експорти можна явно передати:

```sh
.venv/bin/python src/social_cli.py --import-posts /absolute/path/posts.jsonl
```

Соціальний експорт має містити `platform`, `post_id`, `account_handle` або
`author_id`, `timestamp`, `text`. Підтримані також назви `source`, `id`,
`created_at`/`date`, `username`/`author`, `text_content`. Якщо є лише ID,
індексується ID, а неповні дані відображаються лічильником `id_only_records`.

Індекс `existing_ids` має точний ключ `(platform, post_id)`. Це SQLite B-tree
із пошуком O(log n), не Bloom Filter: немає хибних позитивних результатів
і немає потреби тримати всі ID в оперативній пам'яті. Bloom Filter можна
додати як попередній кеш, але позитивний результат треба перевіряти в точному
індексі, інакше можна втратити нові дописи.

`content_hash` — MD5 канонічного JSON-масиву `[platform, author, text, timestamp]`.
Крім MD5, порівнюється весь канонічний вміст, тому колізія MD5 не видалить
відмінний допис. Час нормалізується в UTC, текст — NFC і LF без обрізання
пробілів. За наявності ID автора й handle зберігаються обидва ключі, щоб
зіставити старі експорти без ID автора. Зміна і handle, і ID потребує окремого
підтвердження тотожності автора. Збіг тексту/автора/часу під різними ID
трактується як дублікат відповідно до заданого правила; різні публікації
з абсолютно однаковими значеннями цим правилом не розрізняються.

Відомий ID перевіряється до витягування тексту/медіаданих і до збереження.
Отримати список ID та часові поля з API все одно необхідно. API може
повернути вже відомі записи: локальна дедуплікація не усуває мережевий трафік
або оплату такого запиту. Старі дописи не копіюються до нового експорту.

## Завдання і відновлення

`worker_tasks.jsonl` містить параметри завдань, контрольну суму початкового
індексу, шлях до спільного точного індексу, стан, курсор, останній ID і час.
Індекс залишається живим: контрольна сума описує знімок під час планування,
а нові записи стають видимими всім воркерам через базу.

Вікна напіввідкриті: `[start,end)`. X починається з дати створення,
підтвердженої API. До визначення профілю попередні вікна мають стан
`awaiting_account_metadata`, а нижня межа — `unverified_platform_lower_bound`.
Threads не повертає дату створення публічного профілю; використовується явна
консервативна нижня межа запуску платформи, яка не видається за дату акаунта.

Сторінка, індекс дублікатів і наступний курсор фіксуються однією транзакцією.
Після збою повторюється лише незавершена сторінка. Якщо курсор протерміновано,
точне продовження з нього неможливе: вікно переглядається з початку з
дедуплікацією. Автоматично дозволено один такий перезапуск на завдання.
Повторені курсори та застарілі результати паралельних воркерів відхиляються.
Поточний CLI виконує одного воркера послідовно; не запускайте кілька CLI
для тієї самої бази, щоб не витрачати API-запити на однакові завдання.

Історичний режим **не зупиняється на 20 дублікатах**: нижче можуть бути
прогалини. Поле `max_consecutive_duplicates_stop: 20` присутнє у завданні,
але `early_stop_allowed: false`. Якщо явно ввімкнути евристику в іншому режимі,
зупинка має стан `paused_duplicates_incomplete`, а не завершено.
`latest_parsed_date` та `oldest_parsed_date` показують межі збережених дописів,
але не підтверджують суцільного покриття між ними.

## Що означає повнота

`api_exhausted` означає завершення пагінації X full-archive API у вікні.
`partial_source_exhausted` означає вичерпання обмеженого джерела Threads.
Жоден стан не доводить наявність усіх коли-небудь публічних дописів:
видалені, приховані та недоступні джерелу записи можуть бути відсутні.

Threads public profile API має обмеження для профілів, зокрема поріг
100 підписників; відповіді до профільної видачі не входять. Отже, поточний
адаптер Threads не може забезпечити повну історію разом з усіма відповідями.
Окремих файлів фото/відео колектор не завантажує; зберігає повернені API поля
дописів. `new_posts.csv` і `new_posts.jsonl` містять усі нові записи цієї бази
накопичувально, без повторних рядків між запусками.
