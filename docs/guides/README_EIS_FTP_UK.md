# Контракти ЄІС із FTP → NDJSON

`src/eis_ftp_contracts.py` працює на Python 3.9+ без сторонніх пакетів. Використовує
`ftplib`, `asyncio.to_thread`, `zipfile.ZipFile.open` та `ElementTree.iterparse`.
FTP-вхід завжди `anonymous` / `anonymous`, пасивний режим.

## Запуск

```sh
python3 src/eis_ftp_contracts.py --output contracts.ndjson --days 1 --concurrency 3
```

За замовчуванням: обидва закони, усі регіональні каталоги, усі частини архівів
за останню доступну дату щоденної вигрузки в кожному регіоні. Це остання дата,
наявна на сервері, а не гарантія актуальності на сьогодні. Дати беруться з назв
архівів; місячні й річні інтервали відкидаються. Якщо дата в назві відсутня,
використовується FTP `modify`, коли сервер її надає.

Лише 44-ФЗ:

```sh
python3 src/eis_ftp_contracts.py --laws 44 --days 3 --output contracts44.ndjson
```

Локальні архіви, без мережі:

```sh
python3 src/eis_ftp_contracts.py --local-zip archive1.xml.zip archive2.xml.zip --local-law 44 --output local.ndjson
python3 src/eis_ftp_contracts.py --local-zip archive223.xml.zip --local-law 223 --output local223.ndjson
```

## Каталоги та версії XML

Корені згідно із запитом: `/fcs_regions` та `/dish`. Наявність і призначення
`/dish` для контрактів 223-ФЗ **не підтверджені**. Скрипт не трактує файли
реєстру недобросовісних постачальників як контракти. Під час перевірки
10.10.2026 підключення до `ftp.zakupki.gov.ru` із цього середовища завершилося
DNS-помилкою; живу структуру каталогів і схеми перевірити не вдалося.

Корені змінюються через `--root44` / `--root223`. Для перевіреного історичного
дзеркала, яке використовує `/out/published`, можна явно задати:

```sh
python3 src/eis_ftp_contracts.py --laws 223 --root223 /out/published --remote-dir contract/daily --output contracts223.ndjson
```

Без `--remote-dir` перевіряються лише регіональні підкаталоги `contracts/currMonth`,
`contracts`, `contract/daily`, `contract`; загального рекурсивного сканування немає.
Опцію `--remote-dir` можна повторювати. Відсутні підкаталоги пропускаються,
регіони без щоденних контрактних архівів зазначаються в журналі. Якщо архівів
не знайдено взагалі, запуск завершується помилкою.

`--regions` приймає точні назви регіональних каталогів FTP. Обмеження лише
регіонами реєстрації цільових підприємств може втратити контракти, де вони
постачальники для замовників інших регіонів. Тому типовий режим охоплює всі регіони.

XML-шляхи із `PATHS` є явними адаптерами: 44-ФЗ `customer`, `suppliers/supplier`,
`price`, `signDate`, `products`; 223-ФЗ — зокрема
`body/item/contractData/supplierInfo`, `contractDate`, `contractPositions`.
Префікси просторів імен не впливають на розбір. Поточну версію XSD ЄІС на
живому сервері не перевірено. Для іншої структури задайте `--paths-json mapping.json`,
наприклад:

```json
{"223":{"customer":["body/item/contractData/customer"],"id":["body/item/contractData/contractRegNumber"]}}
```

Шляхи відносні до вузла контракту; невказані поля адаптера залишаються типовими.
Невідомий тип документа викликає помилку. Відомий тип із невідповідними шляхами
може дати нуль збігів — для нової XSD слід перевірити адаптер на зразку XML.

## Фільтрація та вихід

Один рядок відповідає одній парі замовник–постачальник. Усі вісім полів завжди
присутні; відсутні реквізити — JSON `null`. Ідентифікатори та ІПН — рядки.
Дата нормалізується до `YYYY-MM-DD`; некоректна дата дає `null`.
Ціна — точне JSON-число, сформоване через `Decimal`, без округлення через `float`.
У 223-ФЗ невідома валюта або валюта, відмінна від RUB/RUR/643, дає `price_rub: null`;
конвертація курсів не виконується. У 44-ФЗ поле `price` без явної валюти
трактується як рублеве відповідно до запитаного формату.

Умова відбору буквально така:

```text
(customer_inn ∈ targets AND valid_checksum(supplier_inn))
OR (supplier_inn ∈ targets AND valid_checksum(customer_inn))
```

ІПН обох сторін мають містити 10 або 12 цифр. Анонімний постачальник
відкидається. Контрольні цифри перевіряються для протилежної до цільової сторони.
Чотири задані цільові ІПН не проходять перевірку контрольних цифр:
`1646019864`, `2128700223`, `1804002498`, `6612001460`. Їх збережено без виправлень
як вхідні пошукові ключі; при запуску виводяться попередження.
Для суворої перевірки **обох** сторін виправте вхідні ІПН за первинними документами.

Сума належить контракту в цілому й повторюється в рядках різних постачальників:
такі рядки не можна просто сумувати. Версії контрактів у різних архівах не
дедуплікуються; порядок рядків за паралельного завантаження не гарантований.

## Пам'ять, помилки та перевірка

На диск тимчасово записується лише стиснений ZIP та відібрані NDJSON-рядки.
XML читається без вилучення файлів на диск. Пам'ять обмежена переважно одним
вузлом контракту на працівника; один дуже великий контракт також потребує пам'яті.
Ліміти задаються через `--max-zip-mib` та `--max-xml-mib`.
DTD та оголошення сутностей відкидаються. FTP-завантаження мають тайм-аут
і повторні спроби, кожен працівник використовує окреме з'єднання.

Після успішної обробки всіх архівів вихідний файл атомарно замінюється.
Помилка завантаження, ZIP або XML залишає попередній результат незмінним
і повертає код завершення 1. Тимчасові дані очищаються при звичайному завершенні.

```sh
python3 -m unittest discover -s tests -p test_eis_ftp_contracts.py -v
```

11 автономних тестів перевіряють адаптери 44/223-ФЗ на синтетичних XML,
фільтрацію обох напрямків, контрольні цифри, `null`, простори імен, дати
архівів, вибір усіх частин щоденної вигрузки, DTD та атомарність результату.
Ці тести не підтверджують доступність FTP або відповідність поточній XSD ЄІС.
