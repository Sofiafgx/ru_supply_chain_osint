# Парсер повірок АРШИН

`src/arshin_parser.py` шукає обладнання за маркерами, завантажує картки повірок,
перевіряє власника/замовника та зберігає підтверджені збіги.
Залежність `httpx>=0.27` уже є в `requirements.txt`.

```sh
python3 src/arshin_parser.py
```

ІПН за замовчуванням: `2128700223`, `1804002498`, `6612001460`, `6444009038`.
Вони використовуються буквально, без заміни на ІПН інших підприємств.

## Проксі та запити

Файл `config/private/proxies.txt`: один HTTP-проксі на рядок. Формати:
`http://user:password@host:10000`, `host:10000`, `host:10000:user:password`.
Паролі у URL мають бути URL-кодованими. Порожні рядки й коментарі `#` ігноруються.
До пулу включаються лише наявні адреси з портами **10000..10999**;
відсутні порти не генеруються. Пул впорядковано за портом; кожен запит/повтор
переходить до наступного проксі.
Сесії `httpx.Client` перевикористовуються; одночасно відкрито максимум 16.
Використовується `verify=False`, прямого резервного з'єднання немає.
Адреси/паролі проксі не друкуються в повідомленнях помилок.
HTTP 429/499/502/503/504 повторюються до 5 спроб із паузами 3, 6, 12, 12 с
та зміною проксі. `Retry-After` може збільшити паузу до 30 с.
Порти з 429/499 або транспортним збоєм виключаються до наступного запуску.
Таймаути: з’єднання/запис — 15 с, читання — 50 с, пул — 30 с.
`--read-timeout`, `--timeout`, `--retries` дозволяють змінити ці межі.
Після вичерпання спроб/пулу процес завершується зі звітом `status: failed`.

Заданий `cm/xcdix/vri` перевіряється першим. Якщо він повертає HTML,
невідому JSON-структуру або HTTP 404/405, використовується
`cm/xcdb/vri/select`. Обидва шляхи перевірено 10.10.2026: перший повертав
HTML, другий — `response.docs` / `response.numFound`.
Картки: `cm/iaux/vri/{vri_id}`. Ендпоінти можна змінити через
`--search-url` та `--detail-url` (останній має містити `{vri_id}`).

## Відповідність замовника

`org_title` та `vriInfo.organization` — **повіритель**, тому вони не
використовуються як доказ належності обладнання заводу.
Перевіряються лише `vriInfo.miOwner` і `miOwnerInn`.
За відсутності ІПН допускається однозначний точний збіг з назвою,
заданою користувачем. Регістр, лапки й пунктуація нормалізуються;
початкові АО/ОАО/ЗАО/ПАО/ООО та «АКЦИОНЕРНОЕ ОБЩЕСТВО» ігноруються.
Назви інших юридичних осіб, філіалів або суперечливий ІПН не приймаються.

Для карток, які містять лише назву власника, створіть JSON відповідностей:

```json
{"6444009038": ["ТОЧНА ПЕРЕВІРЕНА НАЗВА ПІДПРИЄМСТВА"]}
```

```sh
python3 src/arshin_parser.py --facility-names config/facility_names.json --year 2025
```

Без цього файлу збираються тільки картки з явно зазначеним цільовим ІПН.
Відсутність збігів не означає відсутності обладнання: назви без ІПН,
непублічні власники й картки партій/еталонів не підтверджують окремий прилад.
ІПН власника не є підтвердженням конкретного місця експлуатації приладу.

## Вихід і повнота

`data/processed/equipment/verified_equipment_arshin.jsonl` містить рівно ці поля:
`facility_name`, `facility_inn`, `verification_date`, `equipment_type`,
`equipment_modification`, `equipment_serial_number`, `verification_result`, `vri_id`.
Дата — `YYYY-MM-DD`; результат — `придатний` / `непридатний`.
Модель і серійний номер беруться тільки з `miInfo.singleMI` картки;
за відсутності або значень «нет данных», «б/н» тощо записується JSON `null`.
Засоби, використані для повірки (`means`), не є цільовим обладнанням.
Повторні `vri_id` пропускаються; інші повірки того самого приладу зберігаються.

Пошук охоплює назву, позначення типу й модифікацію обладнання; локальна
перевірка маркерів виконується повторно за карткою.
Оскільки власник не представлений у перевіреній пошуковій відповіді,
парсер обходить кандидатів за обладнанням і перевіряє власника окремо.
Повний збір може бути тривалим. Для пробного запуску:

```sh
python3 src/arshin_parser.py --rows 1 --max-pages 1
```

`--max-pages` обмежує збір і не означає повної перевірки реєстру.
Файл `data/processed/equipment/verified_equipment_arshin.jsonl.report.json` містить `run_id`, `status`, `complete`,
час оновлення, кількість кандидатів, карток, нових збігів та запитів.
Звіт скидається на початку обходу й оновлюється після кожної картки,
пошукової сторінки, повторної спроби та при помилці.
`previously_saved` — кількість уже збережених унікальних записів на старті;
`matched` — тільки нові записи поточного запуску. Порожній JSONL із
`complete: false` не можна трактувати як відсутність повірок.
Пагінація впорядкована за `vri_id`; реєстр може змінюватися під час збору,
тому це не гарантує незмінного історичного знімка.

Проміжний `.jsonl.partial` відкривається в режимі дозапису; кожен запис
одразу скидається через `flush()`. Непорожній файл зберігається між запусками.
У разі помилки наявний основний JSONL залишається; нові рядки — у `.jsonl.partial`.
Наступний запуск обходить пошук спочатку й пропускає вже збережені `vri_id`.
Після успішного заданого обходу основний та проміжний файли об’єднуються
без дублікатів через атомарну заміну; попередні записи не втрачаються.
Для різних списків цілей/років використовуйте окремий `--output`, оскільки
раніше збережені записи не відфільтровуються повторно під час об’єднання.
